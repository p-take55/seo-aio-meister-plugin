# サイトの受け皿を調べる

良い記事を出しても、サイト側が整っていなければ引用されない。記事を出し始める前に 1 回、その後は作りが変わったときに行う。

## 1. 機械で確かめる

```bash
python3 scripts/site_check.py 〈サイトの URL〉 --prefer 〈記事フォルダのパス。例 /blog/〉 --pages 8
python3 scripts/site_check.py 〈サイトの URL〉 --url 〈見たいページの URL〉 --url 〈もう 1 つ〉   # ページを名指しする
```

サイトの URL は `docs/seo-settings.md` の値を使う。`--url` で名指ししたページは、`--pages` の数とは別に必ず調べる（`--pages 3 --url 〈1 件〉` なら 4 ページ）。

次のことが分かる。

- robots.txt が、検索と AI のクローラーを許可しているか（トップページ、記事フォルダ、調べた各ページについて）
- クローラーの名乗りでアクセスしたとき、サーバーや CDN が拒否しないか
- サイトマップがあり、ページが載っているか
- ページごとの題名・説明・言語・正規 URL・noindex・構造化データ・著者・日付・本文の量

読み方:

- robots.txt の欄は、クローラーごとに 1 行。「許可」は、トップページ・記事フォルダ・調べた全ページで許可。「一部拒否」は、拒否されたパスが同じ行に出る。「拒否」は、トップページから拒否。
- サイトマップの「更新日つき」は、更新日（`lastmod`）が書かれている URL の数。0 でも欠陥ではないが、記事には付いているほうが、変更が早く伝わる。
- **拒否して困るのは、検索用のクローラー**（Googlebot、Bingbot、OAI-SearchBot、Claude-SearchBot、PerplexityBot と、利用者の求めで開く ChatGPT-User・Claude-User・Perplexity-User）。robots.txt がこれらを拒否していれば、AI の回答に出ない。
- **「名乗りだけ拒否」は、欠陥と決めつけない。** スクリプトは名乗りを変えて開くだけで、本物のクローラーではない。偽の名乗りを止める CDN の設定に当たると、本物は通っているのに拒否と出る。逆に、名乗りは通っても本物だけを止める設定もある。robots.txt の拒否は「止める」に、名乗りだけの拒否は「確かめられなかったこと」に置き、サーバーや CDN の設定を人間に確かめる。
- **学習用のクローラー**（GPTBot、ClaudeBot、Google-Extended、Applebot-Extended、CCBot）の拒否は、会社の方針のことがある。欠陥として扱わず、意図したものかを人間に確かめる。
- 「本文の文字数」が少ないページは、画面を JavaScript で描いているおそれがある。AI のクローラーの多くは JavaScript を動かさない。
- サイトマップが無いサイトでは、トップページのリンクから拾ったページだけを見ている。記事フォルダがトップからつながっていないと、記事は 1 本も調べられていない。サイトマップはあっても、記事フォルダが載っていないサイトでも同じことが起きる。調べたページの一覧に記事が 1 本も無ければ、記事の URL を `--url` で名指しして、もう一度動かす。
- 判定の項目だけでは、ページの中身が自社のものかは分からない。次の「目で確かめる」で本文を読む。

## 2. 目で確かめる

スクリプトで分からないことを、Project の repo とページの本文で見る。

- **ひな形の残り**: サイトを作ったときの見本が残っていないか。市販のひな形から作ったサイトでは、次が残りやすい。
  - サイト全体の既定の題名・説明が、ひな形の製品名や別の言語の定型文のまま。多くのページに広がる。
  - サイトの URL の予備の値が、ひな形の配布元のドメインのまま。本番で設定が抜けると、共有用の URL や画像がよそのドメインを指す。正規 URL を足す前に、ここを直す。
  - 見本の記事、見本の著者名、共有用の見本の画像。
  - メニューからつながっていない会社概要・料金・採用・問い合わせのページに、架空の人物・数字・料金・送信先の無いフォームが残っている。リンクが無くても検索に載りうるので「止める」に入れる（AI が誤った料金や会社の情報を引く）。
  - 正規 URL や構造化データを出す仕組みが用意されているのに、どこからも使われていない。
  - 存在しないページが、404 を返さずに別のページへ転送される。
- **運営者と著者**: 会社の概要、所在地、問い合わせ先があるか。記事に著者名があり、その人が誰かが分かるページがあるか。
- **記事の体裁**: 記事ページに、公開日・更新日・著者・構造化データ（`Article` または `BlogPosting`）が出る作りか。記事を足すと自動で付くか、1 本ずつ手で書く必要があるか。
- **導線**: トップページやメニューから、記事の一覧に行けるか。記事どうしがリンクでつながる作りか。
- **言語**: ページの言語の指定が、本文の言語と合っているか。

## 3. 重さで分ける

| 重さ | 意味 | 例 |
|---|---|---|
| 止める | 直すまで、記事を出しても効果が出ない | 検索用のクローラーを拒否、noindex、本文が HTML に無い、見本の記事や題名が残っている |
| 効く | 直すと、見つかりやすさと引用されやすさが上がる | サイトマップが無い、正規 URL が無い、記事の構造化データ・著者・日付が無い、記事一覧への導線が無い、言語の指定が違う |
| 任意 | 余裕があれば | llms.txt、よくある質問の構造化データ |

迷ったら軽いほうに置く。「止める」は、放置すると記事作りが無駄になるものだけにする。

## 4. 文書にする

Project 文書 `docs/site-readiness.md` に書く。

```markdown
# サイトの受け皿

確認日: YYYY-MM-DD ／ 対象: 〈URL〉 ／ 見たページ: 〈数〉

## 止める
| 項目 | 状態 | 今の状態 | 直し方 | 根拠 |
|---|---|---|---|---|
| 〈例: 題名がひな形のまま〉 | 未／済（YYYY-MM-DD に公開中のページで確認） | 〈実際の値〉 | 〈どのファイルの何を、どう変えるか〉 | 〈スクリプトの出力、またはファイルと行〉 |

## 効く
（同じ形）

## 任意
（同じ形）

## 問題なし
- 〈確かめて、問題が無かった項目〉

## 確かめられなかったこと
- 〈例: 送信元で本物のクローラーだけを止める設定の有無〉
```

「直し方」は、開発者がそのまま着手できる具体さで書く。repo を読めるなら、ファイル名まで書く。

## 5. 動く

- 「止める」が 1 つでもあれば、記事作成を始める前に人間に報告する。直すのは開発者か、依頼された Agent。自分で repo を直すのは、依頼されたときだけにする。
- 学習用のクローラーの扱いなど、方針の判断が要るものは Ask で聞く。
- 直したと聞いたら、スクリプトをもう一度動かして、公開中のページで確かめ、この文書の「状態」を直す。repo の変更だけを見て「済」としない。直ったかどうかは、この文書を正とする。
- サイトマップが足されたら、Search Console に送るよう人間に伝える（「サイトマップ」の画面に、サイトマップの URL を入れる）。

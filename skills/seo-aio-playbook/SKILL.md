# SEO・AIO の進め方

サイトが検索と AI の回答で引用され、事業につながる流入を得るまでを、通して進める。事業を調べ、サイトを整え、戦略を決め、書くべき問いを選び、記事を書き、確かめ、結果を測り、戦略を直す。

「AI の回答での引用」として測るのは、Google の検索結果に出る「AI による概要」が引用しているサイト。ChatGPT や Perplexity などは、そこからサイトに来た訪問の数だけを見る。測っていないものを、測ったように書かない。

## 一巡

| 段階 | すること | 使う skill |
|---|---|---|
| 0. 準備 | 始める前に、何があり何が無いかを確かめる。データ源をつなぐ | `seo-setup`、`seo-data-connect` |
| 1. 事業調査 | 事業・顧客・競合・自社だけの根拠を整理する | `seo-business-research` |
| 2. サイト整備 | サイトが検索と AI に読まれる状態かを調べる | `site-readiness-audit` |
| 3. 戦略 | 狙うテーマと記事の組み方を決め、人間の承認を得る | `keyword-strategy` |
| 4. キーワード選定 | 承認された戦略の中から、今書くべき問いを選ぶ | `keyword-discovery`、`keyword-evidence`、`ai-citation-check` |
| 5. 記事作成 | 根拠を付けた概要を作り、記事を書く | `article-brief`、`article-writing` |
| 6. 受け入れ確認 | 書いた記事を、公開の前に確かめる | `article-acceptance-check` |
| 7. 効果測定 | 記事の結果と、AI の回答での見え方を見て、次の手を決める | `seo-results-review`、`ai-visibility-tracking` |

数字は `seo-data-sources` で取り、`seo-database` で Project のデータベースにためる。集めた状況と数字は、`seo-dashboard` で 1 枚の画面にして人間に見せる。

## 今どの段階かを見分ける

依頼を受けたら、まず Project の文書から確かめる。前の段階が済んでいなければ、そこから始める。

| 番号 | 段階 | そこにいる条件 |
|---|---|---|
| 0 | 準備 | 設定の文書（`docs/seo-settings.md`）がまだ無い |
| 1 | 事業調査 | 事業の概要がまだ無い（未確認の項目が残っていても、文書があれば「ある」とする） |
| 2 | サイト整備 | 事業の概要はあるが、サイトの受け皿の文書がまだ無い |
| 3 | 戦略 | 戦略が承認されていない |
| 4 | キーワード選定 | 戦略は承認済みで、書くと決まった問いの概要がまだ無い（候補を出している間と、最初の記事の承認を待っている間を含む） |
| 5 | 記事作成 | 概要があり、原稿がまだ無い・書いている |
| 6 | 受け入れ確認 | 原稿があり、受け入れの記録がまだ無い |
| 7 | 効果測定 | 公開した記事があり、結果を見ている |

0〜3 は、いくつも当てはまるときは、いちばん小さい番号にする。4 以降は記事ごとに繰り返すので、Project の段階は、いちばん先に進んでいる記事に合わせる（1 本が受け入れ確認待ちで、次の 1 本を選んでいる最中なら 6）。記事ごとの状態は、候補の文書の「状態」と、画面の記事の一覧に書く。

サイトの受け皿に「止める」が残っていることは、段階を変えない。3 と 4 は進めてよいが、5 で記事を書く前に人間に報告する。

- 2 は 3 と並行で進めてよい。
- 承認前の戦略で 4 へ進まない。
- **「止める」が残っているかは、サイトの受け皿の文書の「状態」で決める。** 記録には直ったとあるのに文書が「未」のままなら、`site-readiness-audit` で公開中のページを確かめ直し、文書を直してから判断する。記事を書く依頼のときも、書く前に 1 回これを行う。
- 記事が公開されて 4 週間以上たつのに、結果を見た記録が無ければ、ほかの依頼より先に 7 を行う。

### 人間の回答を待っているとき

承認や回答を待つあいだ、同じことを聞き直さない。待たずにできることを進める。

- サイトの受け皿の確かめ直し、画面の更新
- AI での見え方の、定点で見る問いの一覧の案（`ai-visibility-tracking` の 1）
- 次の候補の下調べ（料金のかからない範囲）

何を待っていて、答えが出たら何をするかを、報告の最初に書く。

## 書くことと、確かめて通すことを分ける

**同じ Session の中で、記事を書いて、その記事を受け入れ確認で通さない。** 書いたときの文脈を引きずると、自分の書いた誤りを見落とす。

- `article-writing` を使った Session では、`article-acceptance-check` を使わない。原稿を置いて報告し、そこで終える。
- 受け入れ確認は、新しい Session で行う。人間が「この記事を確かめて」と頼むか、Workflow の次の段にする。
- 書き手が別の Agent や人間のときも、受け入れ確認はこの決まりのとおりに行う。

## 文書の置き場所

会社ごとの情報は、すべて Project の文書に置く。skill の中や、Agent の repo には書かない。

| 情報 | 置き場所 |
|---|---|
| サイトの URL、対象の国と言語、記事の置き場所、記事を書く担い手、データ源 | `docs/seo-settings.md` |
| 事業の概要（事実） | `docs/business-profile.md` |
| サイトの受け皿 | `docs/site-readiness.md` |
| キーワード戦略 | `docs/keyword-strategy.md` |
| 候補の一覧と根拠 | `docs/keyword-candidates.md` |
| 記事の概要 | `docs/briefs/〈短い名前〉.md`（1 本に 1 つ） |
| 記事の原稿 | サイトの repo の作業ブランチ。repo が無ければ `docs/drafts/〈短い名前〉.md` |
| 選んだ問い・受け入れの判断・結果の確認・データ源の接続の経緯・使った額の記録 | `docs/seo-log.md`（追記する。形は `seo-setup` の「記録の文書」） |
| AI での見え方（問いの一覧と記録） | `docs/ai-visibility-panel.md`、`docs/ai-visibility-log.md` |
| たまっていく数字（キーワードと検索数・単価・状態、問いごとの検索結果と引用元、日ごとの検索の数字、使った額） | Project のデータベース（`seo-database`）。使えない Project では文書 |
| 人間が見る画面 | Project HTML の `seo-dashboard.html`（メンバーが開くとデータベースを読む。写しは `seo-dashboard.data.json`） |

Project の REPORT.md は、Session の `aachat/contracts/report.md` の形で、今の状態だけを書き直す。記録を追記する場所ではない。追記する記録は `docs/seo-log.md` に置き、REPORT.md からリンクする。

## 判断の基準

- **戦略の外は選ばない。** 戦略に無いテーマは、検索数が多くても選ばない。有望だと思ったら、戦略の見直しとして人間に提案する。
- **問いで選ぶ。** 人が検索や AI に実際に投げる言い方（「〜とは」「〜 やり方」「〜 比較」「〜できない」）を単位にする。
- **勝てる理由を必ず書く。** その問いに、この会社が他より良く答えられる根拠（独自のデータ、実績、現場の経験、製品の機能）を事業の概要から引く。引けない問いは選ばない。
- **検索数だけで並べない。** 候補を並べるときは、検索数と推移に加えて、買う気の強さ（検索広告のクリック単価）と、AI に引用される余地を見る。単価が高い問いは、検索数が小さくても順を上げる。ただし、単価が高いだけで勝てる理由が無い問いは選ばない。
- **事実と推測を分ける。** 検索数・推移・引用状況には、データの出どころを付ける。推測なら推測と書く。事業の事実を推測で足さない。分からないことは Ask で聞く。
- **人に聞くときは具体から。** 「強みは何ですか」ではなく、「サイトに『〈数〉社に導入』とあります。多い業種はどこですか」のように、事実を名指しして聞く。
- **数より結果で動く。** 記事の本数は目標ではない。効いていないテーマに記事を足し続けない。結果が出るまでの待ち時間（新しい記事は数週間）も、判断に入れる。
- **人間が決めることは人間に返す。** 戦略の承認と変更、最初に書く記事、公開してよい数字や事例、記事を公開すること、費用のかかるツールの契約と入金は、Ask で聞く。

## 進め方の決まり

- Project の文書・Ask・Workflow・Project HTML の操作は、Session 内の `aachat/contracts/` に従う。文書の先頭に置く項目（題、要約など）は `aachat/contracts/docs.md` の決まりで書く。skill のひな形は本文の形だけを示している。先頭の項目の値に「:」や「#」が入るときは、引用符で囲む。
- サイトの repo に書くのは、記事の原稿を作業ブランチに置くときだけ。公開用のブランチに直接入れない。記事以外のコードを直すのは、依頼されたときだけにする。
- 料金のかかる呼び出しは、まとめて 1 回で行い、前後の残高と使った額を報告に書く。上限を言われていれば、届く前に止める。
- データが変わる作業をしたら、最後に `seo-dashboard` で画面を更新する。Project HTML が使えないときは飛ばす。

# 記事の原稿を書く

概要を 1 つ受け取り、その問いに答える記事の原稿を書く。書くのは原稿までで、公開はしない。書いた原稿は、**別の Session** の `article-acceptance-check` で確かめる。この Session の中で、自分の原稿を確かめて通さない。

## 用意するもの

- 記事の概要（Project 文書 `docs/briefs/〈短い名前〉.md`）。無ければ書かない。`article-brief` で先に作る。
- 事業の概要 `docs/business-profile.md`
- 設定 `docs/seo-settings.md`（記事の置き場所、公開までの流れ）
- サイトの repo の既存の記事（書式と、リンクする相手を見る）

## 1. 読む

- 概要の「問い」「読者と段階」「勝てる理由」「抜けている論点」「つなぐ記事」「注意」を読む。
- 概要の「読んだ出どころ」にあるページのうち、書くのに要るものを開き直して読む。何が書かれていて、何が書かれていないかを自分の目で確かめる。写さない。URL が分からず題しか残っていないページは、題で探す。見つからなければ、開けなかったと報告に書く。
- 事業の概要から、この記事で使える事実（数字、実績、機能、現場の経験）を抜き出し、出どころと一緒に並べる。

## 2. 事実を仕分ける

書く前に、記事に入れる事実を 3 つに分ける。

| 種類 | 扱い |
|---|---|
| 事業の概要か、自社のサイト・repo で確かめられる自社の事実 | 書いてよい |
| 出どころの URL を開いて確かめた、他社や世の中の事実 | 書いてよい。本文に出どころを付ける |
| 自社について、事業の概要や公式の案内から読み取ったこと（そのとおりには、どこにも書かれていない） | 記事に要るなら書いてよい。ただし必ず「人間に確かめること」に、書いた文と読み取りの根拠を挙げる。確かめが取れるまで、その記事は公開に進めない |
| 確かめられない事実、概要にも事業の概要にも無い数字・実績・顧客名 | **書かない。** 要る場合は「人間に確かめること」に挙げる |

事業の概要に「未確認」の項目が残っていても、記事が頼る事実が確かめ済みなら、書き始めてよい。未確認の事実には頼らずに書く。

概要の「勝てる理由」が未確認の事実に頼っているときは、その根拠を事実として書かない。それ抜きでは記事が成り立たないなら、書かずに止め、どの事実の確認を待っているかを報告する。

## 3. 骨組みを決める

- **冒頭の 2〜3 文で、問いに答える。** 前置き、背景、「近年〜」から始めない。
- **見出しは、読者の問いの形にする。** 見出しだけ読んで、何に答える節かが分かるようにする。
- **1 つの節は、1 つの問いに答える。** その節だけ抜き出しても意味が通るように書く。「前述のとおり」「これ」で始めない。
- **形を内容に合わせる。** 手順は番号つき、比べるものは表、定義は 1 文で言い切る。
- 概要の「抜けている論点」には、それぞれ節を割り当てる。

## 4. 書く

- **自社の経験は具体的に。** 「多くの企業で」ではなく、いつ、何で、何が起きたか。事業の概要にある範囲で書く。
- **数字には、出どころといつの時点かを付ける。**
- **製品の話は、問いに答えるのに要るところだけ。** 記事の主役は読者の問い。宣伝の段落を足さない。製品で解ける場合は、解けることと、解けないことの両方を書く。
- **他社を悪く書かない。** 比べるときは、確かめた事実と、どんな場合に向くかを書く。
- **言葉は読者のものを使う。** 概要の「問い」の言い方、顧客が使う言葉。社内の呼び名を使わない。
- 長さは、問いに答えるのに要るだけ。水増ししない。

## 5. 体裁をそろえる

サイトの既存の記事と同じ書式にする。既存の記事が 1 本も無いときは、repo の中で記事を表示しているコード（記事の先頭の項目を読んでいる所）から、項目の名前と、必須かどうかを読む。

決まっていない項目（著者、画像など）は、省ける項目なら省き、「人間に確かめること」に挙げる。勝手に埋めない。公開日が必須で、まだ決まっていないときは、書いた日を仮に入れ、仮であることを「人間に確かめること」に挙げる。

表・脚注・注記の書き方は、サイトが変換できるものだけを使う。記事を表示しているコードを読むか、原稿を実際に変換してみて確かめる。Markdown の表を変換しないサイトでは、表を HTML で書く。

- 先頭の項目（題名、説明、公開日、更新日、著者）。項目の名前は、サイトの記事の書式に合わせる。著者は `docs/seo-settings.md` か既存の記事に従い、分からなければ「人間に確かめること」に挙げる。
- 題名は、問いと答えが分かるものにする。説明は、冒頭の答えを 1〜2 文にしたもの。
- 概要の「つなぐ記事」へのリンクを入れる。リンク先が実在するかを確かめる。
- 画像を使うなら説明文を付け、図の中にしか無い情報を本文にも書く。

## 6. 置く

`docs/seo-settings.md` の「公開までの流れ」に従う。

- サイトの repo があるとき: 作業ブランチ（名前は `article/〈短い名前〉`）を作って原稿を置き、push する。流れに PR があれば PR を作る。公開用のブランチには直接入れない。マージもしない。push と PR の記録のしかたは `aachat/contracts/git.md` に従う。
- 「公開までの流れ」が未定のとき: 作業ブランチに置くところで止める。PR を作るか、誰が確かめてマージするかを、報告で人間に聞く。
- repo が無い、または書き込めないとき: Project 文書 `docs/drafts/〈短い名前〉.md` に置く。

## 7. 報告して、ここで終える

返答に次を書く。

- 原稿の場所（ブランチと PR、または文書）
- 概要のどの項目を、記事のどこで満たしたか
- **人間に確かめること**: 確かめられずに書かなかった事実、公開してよいか迷う記述、著者
- 次にやること: 「新しい Session で、この原稿の受け入れ確認を頼んでください」

`docs/seo-log.md` の「選んだ問いと概要」のその問いの行の補足に、原稿の場所を足す。その節や行が無ければ、`seo-setup` の「記録の文書」の形で作ってから足す。

Project のデータベースが使えるときは、その問いの状態を `drafted` に直す（`seo-database` の 3）。

この Session では、受け入れ確認をしない。

## 直しを頼まれたとき

受け入れ確認から直す点が返ってきたら、挙げられた箇所だけを直す。事実の誤りを指摘されたら、同じ種類の記述がほかに無いかも見る。直したら、どこをどう直したかを 1 件ずつ報告し、もう一度、別の Session での確認に回す。

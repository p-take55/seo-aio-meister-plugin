# 記事を受け入れる前に確かめる

見るのは、概要どおりか、事実が正しいか、引用される形になっているか。文章の好みは見ない。本文は自分で書き直さず、直す点を書き手に返す。

**この Session で自分が書いた記事は、確かめない。** 書いたときの文脈を引きずると、自分の誤りを見落とす。同じ Session で頼まれたら、「新しい Session で頼んでください」と返して止める。

## 用意するもの

- 記事の原稿（作業ブランチ、PR、Project 文書 `docs/drafts/`、または Workflow の成果物）。書き手が「人間に確かめること」を挙げていれば、それも読む。作業ブランチにある原稿は、`git fetch` してから `git show 〈ブランチ〉:〈ファイル〉` で読む。確かめたコミットを控える
- その記事の概要（`article-brief` で作ったもの。Project 文書 `docs/briefs/` にある）
- 事業の概要と、キーワード戦略

概要が見つからない記事は、狙った問いを書き手か人間に確かめてから始める。

## 1. 概要と合っているか

- 狙った問いに、記事が正面から答えているか。別の問いの記事になっていないか。
- 概要の「勝てる理由」にある自社だけの根拠が、本文に実際に入っているか。触れただけで中身が無い、は不合格。
- 概要の「抜けている論点」を書いているか。
- 概要の「注意」を守っているか。

## 2. 事実は正しいか

本文から、数字・固有名詞・製品の機能・料金・日付・他社についての記述を抜き出し、1 つずつ出どころと突き合わせる。

- **自社のこと**: 事業の概要、サイト、repo と合っているか。事業の概要に無い数字や実績が書かれていたら、作られたものと疑う。
- **他社や世の中のこと**: 出どころの URL があるか。開いて、そのとおり書いてあるかを確かめる。
- **公開してよいか**: 顧客名、社内の数字、未発表の機能が入っていないか。迷うものは Ask で聞く。

- **出どころの文言どおりに引けない記述は、未確認にする。** 出どころの広い言い方を、特定の話に言い換えた文（「すべて自社で開発」から「〈特定の機能〉を自社で保守している」など）は、読み取りであって事実ではない。
- **出どころどうしが食い違うとき**（公開中のページと社内の資料で、数字や言い方が違うなど）は、弱いほうの言い方に直す点として返すか、未確認にする。強いほうを採らない。
- **出どころのページが読めないとき**（画面で組み立てる作りで、本文が取れないなど）は、公式の仕様書のような別の一次情報で確かめてよい。どちらで確かめたかを書く。
- **製品の画面で確かめられる機能でも、公開中のページに載っていなければ**、記事に書いてよいかは未確認にする。

確かめられなかった記述は「未確認」として一覧にする。未確認が残る記事は通さない。

未確認は、誰が解けるかで 2 つに分ける。

- 書き手が直せば消えるもの（言える範囲に書き直す、出どころを付ける）→ 直す点として返す。
- 人間が答えないと解けないもの（自社の事実、公開してよいか）→ 「人間に確かめること」として、記述・行・確かめられた範囲を一覧にする。Ask を出せるなら Ask で聞く。出せないときは、報告と記録に一覧を残す。

## 3. 引用される形か

AI の回答と検索結果は、問いへの答えが短く取り出せる箇所を引用する。

- **冒頭で答えている**: 最初の 2〜3 文だけで、問いへの答えが分かるか。前置きや背景から始まっていないか。
- **見出しが問いの形**: 見出しを読むだけで、何の問いに答える節かが分かるか。
- **抜き出しても通じる**: 定義、手順、比較が、その段落や表だけ取り出しても意味が通るか。「前述のとおり」「これ」で始まる要点は通じない。
- **形が内容に合っている**: 手順は番号つき、比較は表、定義は 1 文で言い切っているか。
- **自社の経験が具体的**: 「多くの企業で」ではなく、何社で、いつ、何が起きたかが書いてあるか。
- **出どころと日付**: 数字に出どころがあるか。いつの時点の情報かが分かるか。

## 4. サイトに載せる体裁か

- 題名と説明が、問いと答えを表しているか。記事ごとに違うか。
- 公開日・更新日・著者が入っているか（サイトの記事の書式に従う）。
- 同じテーマの記事（柱の記事、関連の記事）とリンクでつながっているか。リンク先は実在するか。
- 画像に説明文があるか。図の中にしか無い情報が、本文にも書いてあるか。
- 既存の記事と、狙う問いが重なっていないか。

## 5. 決める

| 判断 | 条件 | すること |
|---|---|---|
| 通す | 1〜4 に問題が無い | 公開の手順に進めてよいと伝える |
| 直して通す | 中身の直しが小さく、3 つ以内。事実の誤りや未確認が無い。引用の文言やリンクの付け足しのような軽い直しは、この 3 つに数えない | 直す点を返す。直ったら、その箇所だけ見直す |
| 人間の確認待ち | 問いには答えていて事実の誤りも無いが、人間が答えないと解けない未確認が残る | 書き手が直せる点を返し、「人間に確かめること」を分けて一覧にする。答えが出て直ったら、全体をもう一度確かめる |
| 戻す | 問いからずれている、自社の根拠が入っていない、事実の誤りがある | 理由と直す点を返す。直ったら、全体をもう一度確かめる |

返すときは、箇所（見出しや行）、何が問題か、どう直すかを 1 件ずつ書く。行の番号は直すとずれるので、確かめたコミットを添える。「全体的に弱い」のような返し方はしない。

同じ記事を 2 回戻しても直らないときは、概要のほうに問題がないかを見直し、人間に報告する。

## 6. 記録する

Project 文書 `docs/seo-log.md` の「受け入れの判断」に、記事ごとに 1 行で追記する。判断、主な理由、戻した回数、確認日、確かめたコミット。

直す点と未確認の一覧は、その記事の概要の文書（`docs/briefs/〈短い名前〉.md`）の末尾に「受け入れ確認（YYYY-MM-DD、〈回数〉回目）」の節を足して残す。次の確認は、ここを読んで前回の指摘が直ったかを見る。

記事の状態は、通したら「確認済み（公開待ち）」、直す点を返したら「原稿あり」、人間の確認待ちなら「確認中」にする。通した記事は、公開されたら `docs/keyword-candidates.md` の状態を「公開済み」に直し、公開日と URL を `docs/seo-log.md` に書く。
同じ指摘が 3 本以上の記事で続いたら、書き手の指示や Workflow の定義を直す提案として、人間に報告する。
